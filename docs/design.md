# Birth Prep Board — Design Reference

Свіжий погляд на те, що вже задано в `src/app/globals.css` і
`src/components/ui/*`, названий і оформлений як довідник. Наступні
екрани посилаються на цей документ замість дублювання Tailwind-класів
"на око".

## Типографіка

Три ролі шрифту, а не одна гарнітура на все:

- **`font-sans` (Figtree)** — робочий голос інтерфейсу: кнопки, поля,
  текст пунктів чеклиста, весь дрібний UI. Домінує за обсягом тексту
  на сторінці.
- **`font-heading` (Cormorant Garamond, `globals.css` → `layout.tsx`)**
  — гарнітура заголовків, використовується стримано: тільки H1 і
  заголовки карток/секцій, ніколи для основного тексту чи кнопок.
  Реальна шкала ваг (400/500/600) і курсив, обидва підключені з
  `subsets: ["latin", "cyrillic"]` — на відміну від Figtree, у якої
  Google Fonts не має кириличного підмножини взагалі (`layout.tsx`,
  `Figtree({subsets:['latin']})` — свідомо без кирилиці, бо її не
  існує; українські заголовки, якщо колись переведете їх на
  `font-sans`, впадуть назад у системний фолбек).
- **`font-mono` (Geist Mono)** — тільки для числових "зчитувань":
  тижні, дні до ПДР, гроші, дроби прогресу ("3 з 12"). Підключений з
  `cyrillic`, тому можна мішати з українськими словами в одному
  бейджі (напр. "до 26 тижня" у `due-checklist.tsx`) без розсипання
  на фолбек-шрифт.

Базовий розмір тексту в системі — `text-sm` (14px), не `text-base` —
так вже побудовані `Card`, `CardDescription` й інші ui-компоненти.
Використовуйте цю шкалу:

| Клас | Призначення | Приклад |
|---|---|---|
| `text-3xl font-heading italic` (дашборд: `text-4xl`) | Заголовок сторінки (H1) | "Дашборд", заголовок розділу |
| `text-base font-heading font-medium` | Заголовок картки/секції | `CardTitle`-подібні елементи, `DialogTitle`, `SheetTitle` |
| `text-sm` | Базовий текст, весь основний контент | назви пунктів чеклиста |
| `text-sm text-muted-foreground` | Другорядний/описовий текст | `CardDescription` |
| `text-xs text-muted-foreground` | Мета-інформація, підписи | таймстемпи, лічильники |
| `font-mono tabular-nums` | Числове зчитування | тиждень, дні до ПДР, гроші, "X з Y" |

Курсив на H1 — єдине місце, де курсив використовується: підкреслює,
що заголовок сторінки — це "хедлайн", а не просто великий текст;
заголовки карток (`font-medium`, без курсиву) навмисно спокійніші,
щоб не змагатися з H1 за увагу.

## Spacing

Це стосується лише перевикористовуваних компонентів у
`src/components/ui/` — сторінкові layout-файли (`src/app/layout.tsx`,
`src/app/page.tsx`, стаб-сторінки розділів) навмисно хардкодять
звичайні Tailwind spacing-утиліти (`p-4 md:p-8`, `gap-6`, `gap-2`)
напряму, і це очікувана поведінка, не порушення патерну нижче.

Для компонентів у `src/components/ui/` не хардкодять `p-4`/`gap-6`
напряму — вони визначають CSS-змінну на рівні кореневого елемента і
посилаються на неї через `--spacing()`, як `Card` це вже робить
(Tailwind v4 bracket syntax, `card.tsx:15`):

```
[--card-spacing:--spacing(6)]      /* --size=default */
[--card-spacing:--spacing(4)]      /* --size=sm */
```

Для нових складених компонентів (список пунктів чеклиста, рядок
навігації) використовуйте той самий патерн: одна CSS-змінна на
контейнері, а не розкидані утиліти на кожному нащадку — так розмір
компонента можна змінити в одному місці (`data-size` атрибут).

## Радіуси

`--radius: 0.55rem` — базове значення, з якого виведена вся шкала
(`globals.css`). Звужено з попереднього `1rem`: "пухкі" картки
конфліктували з ідеєю вимірювального інструмента (рулетка, mono-дані)
— точніші кути читаються прецизійніше, залишаючись м'якими (не 0,
не broadsheet-стиль):

| Токен | Значення | Де вже використовується |
|---|---|---|
| `rounded-sm` (`--radius-sm`) | 0.33rem | — |
| `rounded-md` (`--radius-md`) | 0.44rem | — |
| `rounded-lg` (`--radius-lg`) | 0.55rem | базові контейнери |
| `rounded-xl` (`--radius-xl`) | 0.77rem | — |
| `rounded-2xl` (`--radius-2xl`) | 0.99rem | `Card` (`card.tsx:15`) |
| `rounded-3xl` (`--radius-3xl`) | 1.21rem | — |
| `rounded-4xl` (`--radius-4xl`) | 1.43rem | `Button`, `Input`, `Progress`-track (pill-форма) |

`Card` — `border border-border` (`card.tsx:15`), не `ring-1
ring-foreground/10` як раніше: тонка "розлінована" межа пасує
ledger-естетиці дашборду краще за розмиту тінь-кільце. `Dialog`/
`AlertDialog`-контент лишається на `ring-1 ring-foreground/5` —
навмисно, це плаваючі поверхні поверх backdrop, не рядки списку.

`Checkbox` (`checkbox.tsx:11`) використовує довільне значення
`rounded-[6px]`, а не токен `rounded-sm` — не завʼязуйте нові дрібні
елементи на цей приклад, якщо потрібен саме токен зі шкали вище.

## Кольори — семантика

Токени вже визначені для обох тем (`globals.css`), нижче — за яким
призначенням їх застосовувати, а не просто перелік. Палітра —
ink-plum (не теракота) на нейтрально-паперовому фоні, з marigold як
єдиним сигнатурним акцентом:

- `primary` — теплий ink-plum (glossary: "чорнило"), для CTA,
  активного стану навігації, індикатора прогресу (`Progress` вже це
  робить, `progress.tsx:48`), тексту H1. Це вже НЕ теракотовий —
  теракота відсунута в `coral` (нижче).
- `signature` / `signature-foreground` — marigold, єдиний сигнатурний
  акцент. Наразі використовується тільки в прапорці "гестаційної
  рулетки" (`week-timeline.tsx`) — навмисно рідко, це і є "одна
  сміливість на сторінку" з дизайн-брифу. Не додавайте його ще кудись
  без причини.
- `coral` / `coral-foreground` — спадкоємець старої теракоти,
  другорядний акцент. Зараз ніде не застосований на дашборді —
  зарезервований на майбутнє (напр. "потребує уваги", якщо колись
  знадобиться відтінок теплішого попередження, що все ще не
  `destructive`).
- `success` — приглушений зелений, **тільки** для стану "виконано"
  (позначений пункт чеклиста), ніде більше.
- `destructive` — видалення власного пункту чеклиста, помилки форм.
- `secondary` / `accent` — теплі нейтральні поверхні: hover-стани,
  неактивні бейджі, другорядні кнопки. Не для акцентів вимоги уваги.
- `muted` / `muted-foreground` — фонові панелі, другорядний текст.
- `sidebar` / `sidebar-*` — власний, трохи інший відтінок фону саме
  для навігаційної панелі (App Shell, Задача 3) — не перевикористовувати
  поза сайдбаром, це навмисно виділяє навігацію з-поміж контенту.
  Токени підтягнуті під ту саму палітру (`primary`/`accent`/`border`),
  а не самостійна кольорова гілка.

`--background`/`--foreground` — нейтральний "paper bone" з низькою
хромою, свідомо не персиково-кремовий: попередня палітра (теракота
на кремовому) читалась як типовий AI-дефолт для будь-якого warm-brief,
а не рішення саме для цього продукту.

## Патерни компонентів

**Пункт чеклиста** (типова структура для 7 розділів): `Checkbox` +
назва (`text-sm`) + опціональна ціна (`text-sm text-muted-foreground`,
вирівняна праворуч) + `Button variant="ghost" size="icon-sm"` для
видалення власного пункту (тільки коли `is_seed = false`, спец §2).

**Прогрес** (дашборд, Задача 4): `Progress` з `ProgressLabel` +
`ProgressValue` для підпису й числа поруч з треком — не окремий
текстовий блок збоку, компонент вже підтримує обидва слоти
(`progress.tsx:54-75`).

**Картка "фокус тижня"** (дашборд, Задача 4): `Card` з `CardHeader` /
`CardTitle` (номер тижня) / `CardContent` (`tip`-текст, `text-sm`).

**Пункт навігації** (App Shell, Задача 3): іконка з `@hugeicons/core-free-icons`
+ підпис, активний стан підсвічується через `data-active:bg-sidebar-accent`
+ `data-active:font-medium` (CLI-generated `sidebarMenuButtonVariants`,
`sidebar.tsx:482`) — фон `sidebar-accent`, а не `sidebar-primary`, і зміна
ваги шрифту, а не кольору тексту.

**Гестаційна рулетка** (дашборд, hero, `week-timeline.tsx`) —
сигнатурний елемент редизайну: горизонтальна вимірювальна стрічка
замість generic progress bar, бо вагітність рахують і вимірюють
тижнями (як стрічкою на кожному огляді), а не просто "заповнюють".
Структура:

- Eyebrow-рядок з трьома триместрами (`I`/`II`/`III триместр`) —
  легітимна нумерація, бо триместри дійсно послідовні й іменовані,
  не декоративні "01/02/03". Поточний триместр — `text-foreground`,
  інші два — приглушені (`text-muted-foreground/60`).
- 40 tick-marks (`div` на тиждень, `flex-1`, без media-query на
  ширину — той самий принцип, що й у старому сегментному варіанті).
  Major-тики (кожні 4 тижні + межі триместрів 13/14/27/28 + 1/40) —
  вищі й підписані номером тижня в `font-mono text-[10px]` кожні 8
  тижнів, щоб не захаращувати мобільний екран. Минулі/поточний тиждень
  — `bg-primary`, майбутні — `bg-foreground/15`.
- Прапорець поточного тижня — абсолютно позиційований над відповідним
  tick, `bg-signature` (єдине використання сигнатурного marigold-акценту
  на сторінці), показує `{weekLabel} тиж · {dueLabel}` в `font-mono` —
  це замінило окремий текстовий рядок тижня/днів над таймлайном, який
  був у `page.tsx` до редизайну.
- Один оркестрований момент анімації при завантаженні:
  `motion-safe:animate-[ruler-grow_...]` на тик-марках (по черзі,
  `animationDelay` з індексу) і `motion-safe:animate-[ruler-drop_...]`
  на прапорці. `@keyframes ruler-grow`/`ruler-drop` — у `globals.css`.
  `motion-safe:` — це вже `@media (prefers-reduced-motion: no-preference)`,
  окремого коду для reduced-motion не треба.
- Форматування `weekLabel`/`dueLabel` (включно з відмінюванням
  "день/дні/днів" і текстом для прострочення) лишається в `page.tsx`
  (`pluralizeDays`) — компонент отримує вже готові рядки, а не дублює
  логіку форматування.

**Рядок "Пора зробити"** (дашборд): один рядок — `ItemToggle`
(чекбокс) ліворуч, далі назва пункту (`text-sm`), одразу за нею назва
розділу (`text-xs text-muted-foreground`, не на `flex-1`, щоб не
відривалась від назви), і `Badge variant="secondary"` з дедлайном
("до N тижня") праворуч. `secondary` — бо це нейтральна інформація про
строк, не привід для тривоги (destructive/яскраві акценти тут навмисно
не використовуються). Понад 8 пунктів — рідний `<details>/<summary>`
("Показати всі (N)"), без нового client-компонента чи маршруту.
Приклад: `src/components/dashboard/due-checklist.tsx`.

**Спільний діалог додавання пункту** (`AddItemDialog`,
`src/components/checklist/add-item-dialog.tsx`): один компонент для
обох місць виклику — дашборд (заголовок блоку "Пора зробити",
`triggerVariant="default"`, бо це основна дія сторінки) і сторінки
розділів (`triggerVariant="outline"`, замінює колишню інлайн-форму в
`SectionChecklist`). Розділ або фіксований пропом `fixedSectionId`
(сторінка розділу — Select не рендериться), або обирається через
`Select` над `SECTIONS_LIST` (дашборд). Поле підрозділу (мама/малюк/
тато) рендериться **умовно** (мовтується/розмонтовується, не
приховується через CSS) лише коли ефективна секція — `hospital-bag`;
список підрозділів бере з єдиної константи `HOSPITAL_BAG_SUBSECTIONS`
(`src/lib/sections.ts`), а не з окремого prop — так дашборд і сторінка
`/hospital-bag` не тримають дві копії того самого списку. Компонент
самодостатній: сам генерує `crypto.randomUUID()`, сам викликає
`addItemAction` у власному `useTransition`. Опційний `onAdd`-колбек
дозволяє викликачу (наразі лише `SectionChecklist`) зробити
optimistic-add у свій локальний список; дашборд його не передає й
покладається на автоматичний refresh від `revalidatePath` усередині
Server Action — той самий принцип, що вже працює для `item-toggle.tsx`.

**Inline-поле `target_week`** (`TargetWeekField`,
`src/components/checklist/target-week-field.tsx`, лише на сторінках
розділів — не на дашборді, де рядок "Пора зробити" завжди має
`target_week` і лишається read-only `Badge`): коли тиждень заданий —
клікабельний `Badge variant="secondary"`, коли не заданий — тиха
кнопка-афорданс (`variant="ghost" size="sm"`). Клік перемикає в режим
редагування: `Input type="number" min="1" max="42"`, збереження по
`blur`/`Enter`. На відміну від інлайн-редагування ціни (яке мовчки
відкочує невалідне значення), тут поза межами 1..42 показується
інлайн-помилка текстом і поле **лишається** в режимі редагування, поки
не введуть коректне значення або не очистять поле (очищення →
`target_week = null`).

**Клієнтський листок замість клієнтського блока** (дашборд): коли
сторінка має лишатись Server Component, а інтерактивність потрібна
лише в одній точці (чекбокс), не обгортайте весь список у `"use
client"` (як робить `SectionChecklist` для одного розділу) — виносьте
саме точку взаємодії в окремий маленький клієнтський компонент з
власним `useOptimistic`/`useTransition` над тим самим Server Action.
Приклад: `src/components/dashboard/item-toggle.tsx` викликає той
самий `toggleItemAction`, що й `SectionChecklist`, залишаючи батьківський
список (`due-checklist.tsx`) серверним.

**Картка розділу з прогресом** (дашборд): `Card size="sm"` обгорнута в
`Link` на маршрут розділу (`className="block"` на `Link`, бо `Card` —
`div`, а `a` за замовчуванням inline), іконка — та сама, що в сайдбарі,
береться з `navItems` (`src/lib/nav-items.ts`) за збігом `href`, а не
дублюється окремим імпортом. Усередині — `CardTitle` (іконка + назва) і
`CardContent` з `Progress` (без лейбла/значення поруч — компактний
рахунок "X з Y" окремим рядком під треком, `text-xs`). Приклад:
`src/components/dashboard/section-grid.tsx`.

**Меню дій рядка пункту** (`DropdownMenu` через shadcn, іконка-тригер
`Button variant="ghost" size="icon-sm"` з `MoreHorizontalIcon`, `render`-проп
замість `asChild` — той самий Base UI патерн, що й у `DialogTrigger`):
завершує рядок пункту чекліста, після бейджа тижня. Пункти зверху вниз:
перемикач `todo ⇄ in_progress` (прихований, коли пункт уже `done` —
чекбокс уже покриває цей перехід), "Додати нотатку"/"Редагувати нотатку"
(лейбл залежить від наявності `note`), "Змінити тиждень" (програмно
вмикає той самий режим редагування, що й клік по бейджу тижня — стан
`editing` піднятий у батьківський рядок, а не локальний для
`TargetWeekField`, саме щоб пункт меню міг його зʼявити). Деструктивне
"Видалити" — окремою групою через `DropdownMenuSeparator`, лише коли
`!item.is_seed`. Приклад: `ChecklistRow` у
`src/components/checklist/section-checklist.tsx`.

**Бейдж "в процесі"**: `Badge` без семантичного `variant` (жоден із
наявних — `default`/`secondary`/`destructive` — не пасує), колір
задається напряму через `className="bg-accent text-accent-foreground"`
— токен `accent`, вже визначений для обох тем, а не новий. `success`
навмисно не використовується: він зарезервований за станом "виконано"
(`.claude/rules` / спец, розділ "Ухвалені рішення"), а `in_progress` —
проміжний стан, не завершення. Рендериться умовно, лише коли
`item.status === "in_progress"`, і на дашборді (`DueChecklist`), і на
сторінках розділів (`ChecklistRow`).

**Нотатка під пунктом** (`src/components/checklist/note-field.tsx`):
трикомпонентний набір — `NoteIndicator` (кнопка-іконка `Note01Icon`,
рендериться лише коли `item.note !== null`, `aria-expanded` відбиває
стан розгортання), `NoteView` (`text-sm text-muted-foreground`,
`pl-7` — вирівнювання під назвою пункту, з відступом чекбокса й
`gap-3`), `NoteEditor` (`Textarea`, збереження по `blur`, порожній
рядок після `trim()` → `null`, не `""`). Рядок пункту — `flex-col`:
перший рядок — стандартні контроли, другий (умовний) — нотатка.
Стан розгортання/редагування — локальний у `ChecklistRow`, не
підіймається вище: сусідні рядки не впливають один на одного.

**Помітка "прострочено"** (`formatWeekBadgeLabel` у
`target-week-field.tsx`, `isTargetWeekOverdue` у `src/lib/pregnancy.ts`):
текстовий суфікс `· прострочено` всередині того самого `Badge
variant="secondary"`, що вже показує дедлайн — без зміни кольору чи
варіанта (спец, розділ 1: без destructive і тривожних акцентів).
Умова: `target_week < currentWeek`. Використовується на дашборді
(`DueChecklist`) і на сторінках розділів (`TargetWeekField`) через
спільну функцію — інакше однакові пункти виглядали б по-різному в
двох місцях. Сторінки розділів обчислюють `currentWeek` з
`pregnancyRepository.getPregnancy` (`null`, якщо вагітності ще немає
— тоді жоден пункт не позначається прострочним).

**Рядок контакту** (`/contacts`, `src/components/contacts/contacts-list.tsx`):
на відміну від пункту чекліста, без чекбокса й статусу — ім'я
(`text-sm`) + роль поруч (`text-sm text-muted-foreground`, лише коли
задана), під ними, якщо є, нотатка (`text-sm text-muted-foreground
whitespace-pre-wrap`, без окремого indicator/expand — на відміну від
`NoteView` у чеклістах, бо в контакту нема сусідніх inline-полів, які
нотатка мала б не зачіпати). Телефон — праворуч, `PhoneField`
(`src/components/contacts/phone-field.tsx`): `tel:`-посилання з
нормалізованим href (пробіли/дужки/дефіси прибрано) і видимим
текстом як ввів користувач; порожній телефон — компонент повертає
`null`, жодної пігулки чи плейсхолдера в рядку (той самий принцип,
що й у `PriceField`, — порожнє поле не рендериться як заповнений
елемент). Меню дій — `DropdownMenu` з двома пунктами, "Редагувати" й
"Видалити" (destructive, окрема група через `DropdownMenuSeparator`),
без умовного приховування — на відміну від чеклістів, у контактів
немає seed-даних, тому видаляти можна будь-який.

**Порожній стан розділу без seed** (`/contacts`,
`ContactsList` при `contacts.length === 0`): контакти — єдиний
розділ MVP без seed-пунктів (`docs/spec.md`, таблиця `contacts`), тож
порожній список — це головний екран при першому відвідуванні, не
крайній випадок з рідким шляхом. Пояснювальний текст (`text-sm
text-muted-foreground`, навіщо розділ і що в нього класти) прямо над
кнопкою `AddContactDialog` з `triggerVariant="default"` — та сама
кнопка, що виводиться під списком (`triggerVariant="outline"`), коли
контакти вже є, лише variant різний, бо в порожньому стані додавання
— головна дія екрана. Приклад ролей — у `placeholder` поля "роль" у
формі (`AddContactDialog`), не в seed-даних бази: набір ролей у
кожної сім'ї свій.

**Підтвердження видалення через `AlertDialog`** (`ContactRow` у
`contacts-list.tsx`): перший і поки єдиний випадок реального
"Ви впевнені?"-підтвердження в проєкті — на відміну від чеклістів,
де `DropdownMenuItem variant="destructive"` видаляє пункт одразу без
підтвердження. Різниця свідома: чекліст-пункт можна додати знову за
секунду, а контакт може тримати єдиний запис номера телефону — ціна
випадкового кліку на "Видалити" в двох випадках різна. `AlertDialog`
(`src/components/ui/alert-dialog.tsx`, Base UI, не Radix — додано
через shadcn CLI зі стилем `base-maia`) відкривається локальним
станом рядка (`deleteOpen`), а не піднятим у список, за тим самим
принципом, що й `weekEditing`/`noteEditing` у `ChecklistRow`: стан
одного рядка не має впливати на сусідні.

**Drag handle в рядку** (`ChecklistRow`, `ContactRow`): окрема
іконка `GripVerticalIcon` (`@hugeicons/core-free-icons`) ліворуч від
чекбокса/імені, а не перетягування всього рядка — на мобільному
жест по всьому рядку конфліктував би зі скролом сторінки. Технічно
це забезпечує `touch-action: none` (клас `touch-none`), який
навмисно застосований **тільки** на кнопці-хендлі, а не на `<li>` чи
`<ul>`: решта рядка (назва, ціна, меню дій) лишається зі звичайним
`touch-action: auto`, тож свайп по тексту пункту чи порожньому місцю
рядка й далі скролить сторінку, і тільки утримання саме іконки
хендла починає drag.

**Сортований список** (`src/components/sortable-list.tsx`,
спільний для чеклістів і контактів): `SortableListProvider` — тонка
обгортка над `DndContext`/`SortableContext` з `@dnd-kit/core` +
`@dnd-kit/sortable` (гілка 6.x/10.x, не переписана `@dnd-kit/react`/
`@dnd-kit/dom`, розділ «Ще не підключено»), яка володіє лише
сенсорами (`PointerSensor` з `activationConstraint: {distance: 8}`,
`TouchSensor` з `{delay: 200, tolerance: 8}` — щоб короткий тап не
запускав drag, `KeyboardSensor` з `sortableKeyboardCoordinates` —
клавіатурне перевпорядкування майже безкоштовне в dnd-kit, не
вимикається) і обчисленням нового порядку на `onDragEnd`
(`arrayMove` + `closestCenter`). Компонент-хук `useSortableRow(id)`
викликається **напряму** в компоненті рядка (`ChecklistRow`,
`ContactRow`), а не проксіюється пропом з іншого компонента: ESLint
React Compiler-правило `react-hooks/refs` вважає `setNodeRef`
(колбек-реф, який `useSortable` повертає поруч з іншими полями)
рефом і забороняє доступ до **будь-якого** поля того самого
об'єкта під час рендеру, щойно об'єкт передається через пропи —
відомий хибний спрацьовує для API на кшталт dnd-kit; тому виклик
рядок звертається до хука сам, і навколо використання `sortable.*`
стоїть точковий `eslint-disable react-hooks/refs` з поясненням.
Список — звичайний `<ul>`, реалізації рендерять власні `<li>` як і
раніше; `SortableListProvider` тільки огортає їх.

**Екран масового редагування** (`/settings/weeks`,
`WeeksEditor` у `src/components/settings/weeks-editor.tsx`): один
екран замість редагування `target_week` по пункту через меню, коли
пунктів багато. Пункти згруповані за розділом (`SECTIONS_LIST`),
перемикач `Switch` "тільки без тижня" (увімкнений за замовчуванням)
фільтрує за **базовим** (уже збереженим) значенням, не за чернеткою
в полі — інакше рядок зникав би просто від набору тексту, а не після
збереження. Валідація (1..42) — при натисканні "Зберегти", по
кожному рядку окремо: невалідні рядки лишаються з інлайн-помилкою
(`text-xs text-destructive` під полем) і чернеткою, решта валідних
змін іде в один Server Action (`bulkUpdateTargetWeeksAction`) і
зберігається. Помилка конкретного рядка знімається одразу при зміні
його поля (`handleChange`), не чекаючи повторного "Зберегти".
Індикатор "Є незбережені зміни" — поруч із кнопкою; додатково
`beforeunload`-guard (лише поки є незбережене) підтверджує вихід зі
сторінки при закритті вкладки чи ручному переході по URL.
