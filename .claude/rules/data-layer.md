# Data Layer

Компоненти ніколи не звертаються до сховища напряму. Тільки через
інтерфейс репозиторію в src/lib/repositories/.

## Контракт

- Один інтерфейс на сутність: ItemsRepository, HouseholdRepository,
  BudgetRepository, PregnancyRepository.
- Інтерфейс описує ЩО можна зробити з даними, і нічого не знає про
  те, ДЕ вони лежать. Жодних згадок localStorage чи Supabase
  у типах, іменах методів чи сигнатурах.
- Реалізацій дві: local (фаза 1) і supabase (фаза 2).
  Перемикання — в одному місці, не в компонентах.

## Async — обов'язково

Всі методи репозиторію повертають Promise, включно з локальною
реалізацією, де це технічно зайве.

Причина: localStorage синхронний, Supabase — ні. Компонент,
написаний проти синхронного доступу, не має loading і error шляхів,
і на фазі 2 його доведеться переписувати. Штучний async зараз —
це те, що робить фазу 2 підміною реалізації, а не переписуванням UI.

Кожен компонент, що читає дані, має явні стани: loading, error,
empty, дані.

## Заборонено

- localStorage / sessionStorage у компонентах
- import конкретної реалізації репозиторію в компоненті
- синхронні гетери даних
- дублювання типів сутностей: тип живе в одному місці,
  реалізації його імпортують

## Фаза 1 — серверна реалізація

Локальна реалізація репозиторію виконується ТІЛЬКИ на сервері.
Сховище — JSON-файл на диску (.data/store.json). Не localStorage,
не sessionStorage, не IndexedDB.

- Кожен файл реалізації репозиторію починається з import 'server-only'.
  Випадковий import у клієнтському компоненті має ламати збірку,
  а не тихо працювати.
- Читання — у Server Components, напряму через репозиторій.
- Запис — тільки через Server Actions, після успіху revalidatePath
  на відповідний маршрут.
- .data/ у .gitignore.

Причина: localStorage зробив би кожну сторінку клієнтською, і
фаза 2 перетворилась би на переписування UI замість підміни
реалізації.

## Одночасний запис

JSON-файл переписується цілком, read-modify-write не атомарний.
Кожна мутація — читання, зміна і запис під одним блокуванням
у межах процесу. Це свідоме спрощення фази 1: на фазі 2 цю роль
бере Postgres.

## Ідентифікатори

id генерує клієнт: crypto.randomUUID(), тип uuid, з фази 1.
Не автоінкремент, не nanoid, не id від сховища.
Причина: інакше optimistic UI на фазі 2 доведеться доробляти
звіркою тимчасового id з реальним.

uuid секцій — константи в src/lib/sections.ts. Ті самі значення
підуть у seed-міграцію фази 2, тому рядкові ключі роутів
('hospital-bag') не є ідентифікаторами.

## Мутації пунктові

Toggle міняє is_checked. Зміна ціни міняє price. Методу
"оновити item цілком" не існує.
Причина: інакше сторінка з протухлим станом перезапише зміни,
які партнер зробив у той самий час.

## Seed-пункти

Матеріалізуються один раз при ініціалізації household.
Не мержаться з bundled-файлу при кожному читанні — інакше правка
seed заднім числом змінює дані наявного користувача.

## Optimistic UI

Мутації через Server Actions з useOptimistic (React 19).
Стани loading, error, empty лишаються обов'язковими попри те,
що локальний запис майже не падає — на фазі 2 error стає
основним шляхом (RLS, протухла сесія, офлайн).
